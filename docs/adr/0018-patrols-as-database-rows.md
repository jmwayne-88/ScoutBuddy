# 0018. Patrols become admin-managed database rows, not a fixed enum

Date: 2026-10-14
Status: Accepted

## Context

[Requirement 8](../requirements/08-manage-patrols.md) asks the ASPL of Camping to be able to view, create, edit, delete, reorder, and activate/deactivate patrols at runtime. Since Iteration 1, patrols have been a fixed Prisma enum (`EAGLE | PUMA | RAVEN | SILVER_FOX | JOE`) — explicitly called out as "fixed reference data" in CLAUDE.md and FEATURES.md, and baked directly into `Menu.patrol`/`MealFrameworkException.patrol` columns, the Patrol Leader's session identity (`lib/session.ts`), every permission check (`lib/permissions.ts`), and a static `PATROLS` array (`lib/constants.ts`) that most of the UI iterated over. An enum value can't be created, renamed, reordered, or deleted without a schema migration and a deploy — the opposite of what admin-managed means.

## Decision

Replace the `Patrol` enum with a real `Patrol` table (`id`, `name`, `color`, `order`, `type: PatrolType` [`YOUTH`/`ADULT`], `isActive`). `Menu.patrol` and `MealFrameworkException.patrol` become `patrolId` foreign keys.

**Migration is hand-written** (`prisma/migrations/20261014142438_patrols_table/migration.sql`), not generated by `prisma migrate dev`'s normal diffing — a plain diff has no way to express "create this table, seed it from the enum's existing values, then backfill every row that referenced the enum," and would simply drop the data. The migration seeds the five patrols that existed at the time (Eagle/Puma/Raven/Silver Fox/Joe) preserving their exact name, color, and order, backfills every `Menu` and `MealFrameworkException` row's new `patrolId` from its old enum value via a `CASE` expression, then drops the old column and enum type. One non-obvious step: the new table is created as `Patrol_new` and only renamed to `Patrol` *after* the old enum type (also named `Patrol`) is dropped — Postgres won't allow a table and an enum type to share a name at the same time, since `CREATE TABLE` implicitly creates a row type of that name too.

**Identity**: a Patrol Leader's session (`lib/session.ts`'s `Actor`) now stores a `patrolId` string instead of a fixed enum value. `getActor()` gained one new check: if the referenced patrol no longer exists (deleted, not just deactivated), the session is cleared and treated as logged-out, rather than left pointing at nothing (REQ-8.14). Deactivating a patrol does *not* clear an already-active session — only deletion does; deactivation only blocks *new* selection (role picker, header dropdown, assigning a fresh menu).

**Deletion is a real, cascading delete**, not soft — a patrol's menus, meals, dishes, ingredients, reviews, and meal-framework exceptions are all removed, following the same manual-cascade style already used by `removeOccasion`/`removeDish` (no `ON DELETE CASCADE` in the schema — see ADR 0012) — gated behind an explicit confirmation dialog naming what will be lost, per the user's decision that deletion should destroy history rather than be blocked, provided the admin is clearly warned first.

**Color is admin-entered, free-form data** — validated at save time against `lib/theme/contrast.ts`'s real `meetsContrast` (4.5:1 against both black and white; rejected if neither passes, per the user's confirmed "block, don't just warn" decision), rather than the looser heuristic in `lib/colors.ts` (`contrastText`) that only *picks* a text color and was never meant to *validate* one. Patrol colors are explicitly not added to `lib/theme/tokens.ts`'s static brand palette — that file governs Scouting America's organizational brand chrome, a different concept from troop-specific patrol identity (a boundary `tokens.ts` already documented before this ADR).

## Alternatives Considered

- **Keep the enum, add a separate "display name/color override" table**: would avoid a data migration, but doesn't actually satisfy the requirement — creating and deleting patrols would still require a schema change, which is the entire problem being solved.
- **Soft-delete patrols (an `isDeleted` flag) instead of a real delete**: rejected per the user's explicit decision — deletion is meant to destroy history, with `isActive` already covering the "hide without destroying" case.

## Consequences

- `lib/constants.ts`'s static `PATROLS` array and `patrolLabel` helper are gone; `lib/patrols.ts` (`getActivePatrols`/`getAllPatrols`) replaces them with a database query, ordered by the admin-controlled `order` column.
- `lib/colors.ts`'s static `PATROL_BACKGROUND` map and `patrolBackground` helper are gone — a patrol's color now lives on its own row and is read directly, not looked up from a fixed table.
- `lib/progress.ts`'s `campoutProgress` no longer has a compile-time patrol count to import; callers now pass the current active-patrol count explicitly.
- `components/PatrolBadge.tsx` takes `{ name, color }` directly instead of an enum value — there's no longer a static lookup to key off of.
- Every future patrol-adjacent feature should assume patrols are ordinary admin-managed data (query `lib/patrols.ts`, never assume a fixed set or a specific count) — the "four/five fixed patrols" assumption this ADR removes should not quietly creep back in.
