# 0032. Direct-to-Blob upload transport for the campout-import file

Date: 2026-10-19
Status: Accepted

## Context

A real user-submitted test file for [Requirement 30](../requirements/data-import/30-campout-import-from-pdf-excel.md) — a two-page troop camping-schedule flyer with twelve illustrated card images — failed to upload once deployed to Vercel, surfacing only as a browser-level "This page couldn't load," not any of this feature's own graceful error messages (ADR 0031's clean-failure design for a bad/unreadable file, REQ-30.2's size-limit message, etc.). That symptom — a raw connection failure rather than an application response — is the signature of a request being rejected at the platform layer before the app's own code ever runs.

The cause: **Vercel Functions (including Next.js Server Actions) have a hard, non-configurable 4.5MB request body limit**, confirmed against Vercel's current documentation. This is entirely separate from, and much smaller than, `next.config.ts`'s own `experimental.serverActions.bodySizeLimit` — that setting only raises *Next's* self-imposed ceiling; Vercel's platform enforces its own 4.5MB ceiling underneath regardless of what Next is configured to allow. REQ-30.2's 15MB file-size cap, and the `bodySizeLimit: "16mb"` set when this feature first shipped, were never actually effective on Vercel — they worked locally (`next dev` has no such platform ceiling) but could never have worked in production for any file anywhere close to that size. A multi-image flyer like the one that surfaced this is a completely ordinary case, not an edge case.

## Decision

**The uploaded file is sent directly from the browser to Vercel Blob storage, bypassing the Server Action's request body entirely.** `components/CampoutImportUploadForm.tsx` calls `@vercel/blob/client`'s `upload()`, which first requests a short-lived, scoped upload token from a new Route Handler (`app/api/campout-import-upload/route.ts` — this app's first-ever API route; everything before this was Server Actions and Server Components, per [ADR 0009](0009-server-actions-for-writes.md)), then uploads the file straight to Blob from the browser. Only once that completes does the client call `uploadCampoutFile` (the existing Server Action) — with just the resulting blob URL and the original filename, a payload of a few hundred bytes regardless of the real file's size. The action reads the file's bytes itself via the SDK's authenticated `get()` (no body-size limit applies to a function's *outbound* requests, only inbound ones) and deletes the blob immediately after reading it, success or failure, via a `try/finally`.

**The Blob store is Private, not Public.** A Vercel Blob store's access mode is fixed at creation and can't be changed afterward, so this is a real, deliberate choice, not a per-upload toggle. A public blob is fetchable by anyone who has (or guesses) its URL, no authentication at all — for a feature that exists specifically because one file briefly held a real troop's full camping schedule, that's a wider exposure window than this app's established posture needs, where every other piece of data is gated behind the role cookie ([ADR 0010](0010-cookie-based-role-identity.md)). Private costs nothing extra here: the SDK's `get(blobUrl, { access: "private" })` reads it just as easily server-side (authenticated via OIDC on Vercel, or `BLOB_READ_WRITE_TOKEN` locally), and since this action never streams the blob back out to a browser — it only ever reads it once, internally, already behind this action's own `canImportCampouts` check — none of private storage's "serve it through an authenticated route" ceremony applies; there's no second route to build.

**Vercel Blob here is transient upload transport, not persistent storage.** This is a different role from the blob-storage option [ADR 0031](0031-campout-import-parsing-extraction-and-merge.md) already considered and rejected for *thumbnails* — that decision (store a resized thumbnail as a `data:` URL in `Campout.imageUrl`, no new storage service) is untouched and still correct; this ADR doesn't reopen it. The uploaded source file itself is never kept anywhere past the single upload action's execution.

**The review/confirm step was redesigned at the same time to avoid resending image data.** The 4.5MB platform ceiling applies to *every* Vercel Function request body, not just the upload — so `confirmCampoutImport`'s payload (the ASPL's edited candidates) was also a latent risk once thumbnails are involved, just a less acute one (text fields are small; several base64 thumbnails on a many-campout import could still approach the limit). Rather than just hoping it stays small enough, the review screen now submits a lightweight `ImportCandidateEdit` per candidate (text fields, the *selected image index*, the discarded flag) — never the `images` array itself. `confirmCampoutImport` re-reads the real candidates (images included) from the `CampoutImportBatch` row already written at upload time, matched back up by `tempId`, and resolves the actual `imageUrl` to write from *that* server-held data. This has a second benefit beyond payload size: a campout's `imageUrl` can now only ever be set from an image this app itself extracted, never from arbitrary bytes a client could otherwise inject into any public POST to this Server Action.

**No change to `next.config.ts`'s `bodySizeLimit`** — it's removed entirely now that neither action's payload is large enough to need raising it above Next's 1MB default, which was itself never the real constraint.

**One Blob store, connected to Production, Preview, and Development alike — not a separate store per environment.** This is a deliberate departure from [ADR 0014](0014-separate-dev-test-database-branch.md)'s dev/test-vs-production database split, not an oversight: that split exists because the database holds real, persistent business data that a dev-environment mistake could corrupt or leak into production. A blob here holds neither — it exists for, at most, the few seconds between a client's upload finishing and this action's `get()`/`del()` pair running, and it's never linked to any other table or read by anything else. There's no production data for a shared dev/preview/production store to put at risk, and Vercel's own default when creating a store (Production + Preview preselected, Development opt-in) already assumes this shared-store shape for exactly this kind of case.

## Alternatives Considered

- **Raise `bodySizeLimit` further / find a Vercel plan-level override**: not possible — Vercel's own documentation and support staff confirm the 4.5MB Function body limit has no configuration flag and is not something a higher plan tier lifts.
- **Shrink `MAX_FILE_BYTES` to safely fit under 4.5MB** (the lighter alternative explicitly offered to and declined by the user): would have "fixed" the crash but made the feature nearly useless for exactly the real-world files it exists for — a multi-campout flyer with photos is a completely ordinary case, not a stress test, and most such flyers would still exceed a sub-4.5MB cap once a few images are involved.
- **Chunked/streaming upload reconstructed server-side**: would avoid the Blob dependency, but is substantially more custom protocol code (client-side chunking, a reassembly endpoint, partial-failure handling) to solve a problem Vercel's own documented, first-party mechanism already solves cleanly.
- **Still resend full candidates (with images) on confirm, just hope it stays under 4.5MB**: rejected once the same root constraint was understood to apply to *every* Function body, not only the upload step — fixing one call site and leaving a structurally identical risk in the other would have been an incomplete fix, found the hard way again for a sufficiently image-heavy import.
- **Public Blob store access**: the simpler default (no server-side auth needed to read it back), but rejected once it was clear `get()` makes private just as easy — public would have meant this feature's one transient file is, for its brief lifetime, fetchable by anyone with the URL, no cookie or role check at all, unlike everything else in this app.
- **A separate Blob store per environment**: considered for consistency with ADR 0014's database split, rejected once the actual reasoning behind that split (protecting persistent, shared data) was checked against this case and found not to apply — see Decision above.

## Consequences

- **A real, required manual setup step**: a **Private** Blob store must be created for this project (Vercel dashboard → Storage → Blob → access: Private) before the import feature works in production — connect it to Production, Preview, *and* Development (Development isn't preselected; add it explicitly, or local dev won't have a token to pull). Creating the store auto-provisions `BLOB_READ_WRITE_TOKEN` for Vercel's own connected environments, but local dev still needs it pulled down by hand (`vercel env pull .env.development.local`, or copied from the dashboard) per `.env.example`'s new entry. Without it, uploads fail with a clear "Invalid upload" message from `uploadCampoutFile`'s own validation rather than a silent crash — a deliberate improvement over the unhelpful browser-level failure this ADR exists to fix. A store's access mode (public/private) can't be changed after creation, so this isn't something to get wrong and fix later without recreating the store.
- This app now depends on a second Vercel-specific service beyond Postgres-via-Neon and the deployment platform itself — worth keeping in mind alongside [ADR 0001](0001-hosted-web-app-architecture.md)/[ADR 0002](0002-nextjs-application-framework.md)'s "no background services" framing, same note [ADR 0021](0021-claude-api-ingredient-categorization.md) made about its own new external dependency.
- This app now has its first `app/api/` Route Handler. Every prior write went through a Server Action ([ADR 0009](0009-server-actions-for-writes.md)); this one specific case (issuing a client-upload token) needed a real HTTP endpoint because that's the shape `@vercel/blob/client`'s `upload()` helper expects to call, not because Server Actions are being abandoned as this app's general write mechanism.
- Unverified in this build environment: the full direct-to-Blob upload path needs a real `BLOB_READ_WRITE_TOKEN`, which wasn't available while writing this fix (same category of local-environment ceiling [ADR 0021](0021-claude-api-ingredient-categorization.md) and [ADR 0031](0031-campout-import-parsing-extraction-and-merge.md) already documented for their own external-service calls). What was verified directly: the code against `@vercel/blob`'s actual shipped type definitions, a full `npm run build`, and that a missing/invalid token produces `uploadCampoutFile`'s own clean error path rather than an unhandled crash.
