# 0033. Passkey-based authentication via Better Auth, superseding cookie-based role identity

Date: 2026-10-23
Status: Accepted; extended by [ADR 0034](0034-account-recovery-token-and-session-invalidation.md), which adds magic-link token invalidation, cross-session revocation on recovery, and the session assurance-tier tracking this ADR's REQ-31.6 scope note deferred.

## Context

[ADR 0010](0010-cookie-based-role-identity.md) gave ScoutBuddy no real accounts — a picker on `/` let anyone declare "I am the ASPL" or "I am the Patrol Leader for X," stored in a plain httpOnly cookie. That ADR explicitly named its own trigger to revisit: "ScoutBuddy is ever used somewhere... shared across multiple troops." [Requirement 27](../requirements/27-multi-tenant-unit-isolation.md) (multi-tenant unit isolation) hit that trigger — it needs a real notion of a person, not just a role, and can't be built on a cookie that carries neither.

[Requirement 31](../requirements/authentication-accounts/31-core-authentication-accounts-sessions-passkeys.md) specifies the replacement in detail, itself the product of a 2026-10-23 research pass checked against NIST SP 800-63B-4 and OWASP ASVS 5.0 — most notably, that finding that email-delivered magic links don't satisfy NIST's AAL2 out-of-band authenticator requirement and can't be treated as equivalent to a passkey. This ADR records the concrete implementation built against that requirement.

## Decision

**Better Auth** (self-hosted, Prisma/Postgres-native) is the auth library, not a hosted IDaaS (Clerk, Auth0) or a second database (Supabase Auth). It's free at any scale — no per-MAU billing — which matters directly for [Requirement 27](../requirements/27-multi-tenant-unit-isolation.md)'s explicit non-commercial, no-per-unit-billing framing; it reuses this app's existing Postgres-via-Neon database (ADR 0003) through the same Prisma client (`lib/db.ts`) rather than adding a second one; and its organization plugin (not used by this ADR, but confirmed available) is what [Requirement 34](../requirements/34-unit-membership-invitations-switching.md) is expected to build on later.

Three packages, pinned to the same version to avoid skew: `better-auth@1.7.12`, `@better-auth/prisma-adapter@1.7.12`, `@better-auth/passkey@1.7.12`. (The passkey plugin and Prisma adapter ship as separate packages from core, not bundled — confirmed by inspecting the installed package, not assumed from documentation.) `@better-auth/cli`'s published versions lag core by several minor versions (1.4.x/1.5.0-beta vs. core's 1.7.12) — its schema-generation command was judged too likely to be stale against this core version's actual plugin schemas, so the Prisma schema below was hand-written from the installed packages' own type definitions and Better Auth's documented stable core shape, then verified empirically by running the real signup/login flow rather than trusted blind.

**Passkey (WebAuthn) is the only standing credential. There is no password authentication anywhere in this app.** [Requirement 31](../requirements/authentication-accounts/31-core-authentication-accounts-sessions-passkeys.md)'s REQ-31.4 (password storage parameters) is satisfied by not building the feature it's conditional on — nothing to hash, nothing to verify. Magic link (`better-auth`'s `magic-link` plugin, `disableSignUp: true`) exists only as a bootstrap/recovery path: it can authenticate an *existing* account but can never create one, enforced at the library-config level, not left as a convention. Sending it requires an email on file, which is itself optional at signup (see Data model below) — an account that skips it simply has no recovery path yet, a real and accepted gap until [Requirement 32](../requirements/authentication-accounts/32-account-recovery-credential-reset.md) builds proper recovery UX.

**Role and patrol live directly on `User`, not a `UnitMembership`.** [Requirement 34](../requirements/34-unit-membership-invitations-switching.md) (which defines `Unit`/`UnitMembership`) doesn't exist yet, and this app is still genuinely single-tenant — so `User.role` (`"ASPL" | "PATROL_LEADER"`, a plain string, not a Prisma enum — Better Auth's `additionalFields` type system is string/number/boolean/date/json only, and fighting that with a native Postgres enum wasn't worth it for an interim field) and `User.patrolId` match today's actual single-unit reality exactly. This is a deliberate interim shape, not an oversight: Requirement 34 is expected to migrate this onto real `UnitMembership` rows once units exist, the same way a person validates `Actor` role today. `lib/permissions.ts`'s `Actor` type (`{ role: "ASPL" } | { role: "PATROL_LEADER"; patrolId: string }`) is **unchanged** — `lib/session.ts`'s `getActor()` now derives it from a real session instead of a cookie, but every one of the ~20 existing call sites across the app needed zero changes. That containment was the explicit goal of building Requirement 31 in isolation rather than bundling it with Requirement 34's unit-membership work.

**Self-service signup, not admin-seeded accounts** (explicit user decision, 2026-10-23, offered as a choice during planning). `/signup` lets anyone with the link create an account and declare a role — the same trust model ADR 0010 already accepted ("anyone with the app's URL can declare themselves the ASPL... an accepted tradeoff"), just backed by a real account and passkey instead of a bare cookie. The actual mechanic: the passkey plugin's `registration.requireSession: false` plus a `resolveUser` callback, fed a small JSON `context` string from the signup form (name, role, patrol, optional recovery email) — the *first* passkey registration IS account creation, since there's no session yet to register a second credential against. This is a deliberate, scoped bootstrap, expected to be superseded by [Requirement 34](../requirements/34-unit-membership-invitations-switching.md)'s real invite system, not a permanent design.

**Step-up assurance is scaffolding only in this build.** REQ-31.6 requires that any action a later requirement marks "sensitive" force a magic-link session to step up to passkey-equivalent assurance — but nothing in the app today is marked sensitive (that's [Requirement 27](../requirements/27-multi-tenant-unit-isolation.md)'s ASPL approve/reject, [Requirement 34](../requirements/34-unit-membership-invitations-switching.md)'s invite management, [Requirement 35](../requirements/35-user-account-disabling-deletion.md)'s account deletion — none built yet). No step-up enforcement is wired into any current page; it's deferred to those requirements, not silently dropped.

**Rate limiting is per-IP (Better Auth's built-in, `storage: "database"` since Vercel's serverless functions don't share in-memory state across invocations) plus a custom per-account check on magic-link requests specifically** (a `hooks.before` middleware matching `/sign-in/magic-link`, backed by the new `AuthEvent` table). Passkey authentication isn't rate-limited per-account, deliberately — it has no "guess the credential" surface the way an email-triggered flow does; REQ-31.7's actual concern doesn't apply there the same way.

**`AuthEvent` is one table serving two jobs**: REQ-31.10's audit log (sign-ins, passkey registrations, account creation) and the per-account rate-limit lookback above — the same rows, queried two ways, rather than two separate tables for what's fundamentally the same "something happened for this identifier at this time" data.

**Resend is this app's first email-sending service**, for magic-link delivery only. Chosen over SMTP/nodemailer for the same reason most of this stack was chosen: one API call, no mail-server configuration, standard in the Vercel/Next.js ecosystem this project already deploys on. Follows [ADR 0005](0005-env-based-secrets-management.md)'s existing env-based secrets pattern (`RESEND_API_KEY`, alongside `ANTHROPIC_API_KEY`/`BLOB_READ_WRITE_TOKEN`); if unset, `lib/email.ts` logs the link to the console instead of sending it, so local development works without a real Resend account — the same "missing external secret degrades rather than crashes" pattern [ADR 0021](0021-claude-api-ingredient-categorization.md) already established.

**OWASP ASVS Level 2 / NIST IAL1** are the explicitly stated targets (REQ-31.8) — written down as a deliberate scope choice, the same way ADR 0010 wrote down its own tradeoff rather than leaving it implicit. IAL1 means no government-ID-grade identity proofing of any account; appropriate given this app's non-commercial scope with no legal or financial stakes, per [Requirement 27](../requirements/27-multi-tenant-unit-isolation.md)'s own framing. Revisit if that framing ever changes.

## Alternatives Considered

See [Requirement 31](../requirements/authentication-accounts/31-core-authentication-accounts-sessions-passkeys.md) itself and the 2026-10-23 research it's built from for the fuller comparison (Better Auth vs. Clerk vs. Supabase Auth on cost; passkey vs. password vs. magic-link on NIST/OWASP assurance grounds; self-service vs. admin-seeded signup, decided by the user during this build's planning). Not re-litigated here.

## Consequences

- This app's identity model fundamentally changes: from "no accounts, a convention the UI helps people follow" to real, individually-held accounts. A person who previously just picked a role each visit now has a persistent account tied to a specific device's passkey.
- A real, required manual setup step, same pattern as [ADR 0032](0032-campout-upload-blob-transport.md)'s Blob store: `BETTER_AUTH_SECRET` must be generated and set in every environment (local `.env`, Vercel Production/Preview/Development), and a Resend account (or at least an API key) is needed for magic-link delivery to actually reach anyone outside local dev's console-log fallback.
- Three new Prisma models beyond this app's own domain (`User`, `Session`, `Account`, `Verification`, `Passkey`, plus this app's own `AuthEvent`) — their field shapes are Better Auth's contract with its Prisma adapter, not this project's naming conventions to vary, which is why they don't follow this schema's usual heavy inline commenting on every field.
- `components/RoleForm.tsx` and `components/RoleSwitcher.tsx` (and `app/(app)/role-actions.ts`) are deleted, not deprecated-in-place — superseded entirely by `components/SignupForm.tsx`/`components/LoginForm.tsx`/`components/AccountStatus.tsx`. CLAUDE.md's MUI-Server-Components-gotcha example list was updated to point at `AccountStatus.tsx` instead of the now-deleted `RoleForm.tsx`.
- Recovery is incomplete by design in this build: an account created without an optional recovery email has no way back in if its passkey is lost, until [Requirement 32](../requirements/authentication-accounts/32-account-recovery-credential-reset.md) is built. This is a known, accepted gap for this requirement's scope, not an oversight.
