# 0031. Campout-upload parsing, extraction, and merge architecture

Date: 2026-10-19
Status: Accepted

## Context

[Requirement 30](../requirements/data-upload/30-campout-upload-from-pdf-excel.md) needs to: read an uploaded PDF or Excel file's text and embedded images server-side; find and extract an arbitrary number of campouts from it without assuming a fixed document shape; match extracted campouts against existing `Campout` rows and propose a merge; and let the ASPL review and edit everything before any write happens. This is this app's second integration with the Claude API (after [ADR 0021](0021-claude-api-ingredient-categorization.md)'s ingredient categorization) and its first time parsing arbitrary uploaded binary files at all.

## Decision

**No new file-storage service.** A thumbnail extracted from the source document is resized/recompressed (via `sharp`, already auto-externalized by Next's `serverExternalPackages` default list) to roughly 800px on its longest side at JPEG quality 75, then stored as a `data:` URL directly in `Campout.imageUrl` — the same plain string column that already only ever held an externally-hosted URL typed into the manual form's "Photo URL" field. At this app's data volume (a handful of campouts a year, per the scale reasoning in [Requirement 27](../requirements/multi-tenancy/27-multi-tenant-unit-isolation.md)'s Architecture Validation section), a few tens of KB of inline image data per campout is immaterial; this avoids standing up Vercel Blob (or any other storage), and the secret/billing surface that would come with it, for a feature that doesn't need it yet.

**PDF text and embedded-image extraction both go through `pdfjs-dist`'s legacy Node build, with no `canvas` dependency.** Text comes from `page.getTextContent()`. Images come from walking `page.getOperatorList()` for `paintImageXObject` calls and reading the already-decoded bitmap via `page.objs.get(...)` — pdf.js decodes embedded images as part of ordinary parsing, independent of ever rendering a page to a canvas. The raw pixel buffer goes straight to `sharp` for resizing/encoding. This was the one piece of this plan that couldn't be verified without writing the code; it was verified by hand (a hand-built test PDF with an embedded raster image, parsed in a standalone Node script) before being wired into the real upload flow, specifically to avoid committing to `canvas`'s native-build risk on Windows ([CLAUDE.md](../../CLAUDE.md)'s own "this is not the Next.js you know" caution, taken seriously here).

**Excel text and embedded-image extraction go through `exceljs`**: cell text is dumped row-by-row per worksheet (no assumed header row or column mapping — REQ-30.7), and `worksheet.getImages()` plus `workbook.getImage(id)` give embedded images' already-encoded bytes directly, filtered/resized by `sharp` the same way as a PDF's images once their real decoded dimensions are known.

**Both `pdfjs-dist` and `exceljs` are listed in `next.config.ts`'s `serverExternalPackages`.** This was discovered the hard way: left to Turbopack's default Server Components bundling, `pdfjs-dist`'s own internal fallback worker setup does a relative dynamic `import()` of `pdf.worker.mjs` based on its *own* on-disk location — bundling moves the calling module into a Turbopack chunk directory where that relative path no longer resolves, surfacing as `Setting up fake worker failed: Cannot find module '.../pdf.worker.mjs'` at request time in `next dev`. Marking the package external makes Next load it via native `require`/`import` straight from `node_modules` instead, where the relative lookup is correct again — the exact reason `sharp` is already on Next's own default external-packages list. `exceljs` was added alongside it as a precaution, for the same category of risk, though it wasn't observed to fail.

**`next.config.ts` also sets `outputFileTracingIncludes` for the two campout-upload routes, forcing `pdfjs-dist`'s whole `legacy/build/*.mjs` set into their deployed function bundle.** `serverExternalPackages` alone fixed `next dev`, but a real Vercel deployment surfaced the same underlying problem one layer further out: `pdf.worker.mjs` is only ever reached via that same dynamic `import()` buried inside `pdfjs-dist`'s own compiled code, which Vercel's automatic file-tracing (`@vercel/nft`, reading Next's own per-route `.nft.json` manifests) doesn't follow — so the file was silently excluded from the deployed function, surfacing as `Cannot find module '/var/task/node_modules/pdfjs-dist/legacy/build/pdf.worker.mjs'` in production even though the exact same code worked locally. `outputFileTracingIncludes`' glob-key matching is `contains`-style (a substring match against the route, not a full-path match), so a single key of `"campouts/upload"` covers both `/campouts/upload` and its nested `/campouts/upload/review/[batchId]` route. Verified directly: after adding this, `pdf.worker.mjs` (and its sibling `.mjs` files) appear in both affected routes' `.next/server/app/(app)/campouts/upload{,/review/[batchId]}/page.js.nft.json` trace files and nowhere else (checked against an unrelated route's trace file, which doesn't carry them).

**One Claude call does both segmentation and field extraction together** (`lib/campout-upload/extract-with-claude.ts`), rather than two passes. The input is the parsed document's text, broken into numbered "sections" (one per PDF page or Excel worksheet) and labeled as such in the prompt; the model is asked to find every distinct campout across all sections — explicitly not assuming one campout per section — and return a JSON array with each campout's extracted fields plus which section(s) it came from. That last field (`sourceSections`) is what lets the upload action pool "nearby" images for a candidate (REQ-30.11) without any pixel-coordinate reasoning: an image extracted from section 3 is offered to any campout the model attributed to section 3.

**The model's reply is parsed as plain JSON text and manually validated**, field by field, rather than relying on `output_config.format`'s structured-output feature — the same posture ADR 0021 took, and for the same reason: this build environment has no real `ANTHROPIC_API_KEY`, so there's no way to observe and verify a live structured-output response shape before committing to it.

**Unlike ADR 0021, there is no non-AI fallback for a failed extraction call.** ADR 0021's ingredient categorization always falls back to a keyword heuristic on any failure, because a rough fallback for "pick one of ten grocery categories" is easy to write and still useful. There's no equivalent fallback for "find and extract an unknown number of campouts from an arbitrary, unstructured document" — a heuristic attempt at that would be more likely to silently produce wrong campouts than to help. A failed call (missing/invalid key, network error, a reply that doesn't parse as the expected shape) instead surfaces a clean, specific error — "Could not extract campouts from this file right now. Please try again later, or add this campout manually." — and nothing is written. This was exercised directly in this build environment (no real key present) and confirmed to degrade exactly this way, both for a PDF and for an Excel upload, rather than crashing or hanging.

**Duplicate matching and merge-preview computation happen once, up front, at upload time** (`lib/campout-upload/match.ts`), not re-derived at confirm time. `matchExistingCampout` requires a case-insensitive exact name match *and* a date within ±2 days; more than one qualifying existing campout is treated as no match at all, left for the ASPL to sort out by hand in review rather than resolved by picking one. `buildMergePreview` then computes the final proposed field values immediately (new upload's non-empty value wins; a blank extraction leaves the existing value alone) and which fields actually changed, so the review screen just displays and edits that result directly, and the confirm action writes exactly what's in the (possibly ASPL-edited) candidate with no second round of merge logic to get out of sync with what was shown.

**A real staging table (`CampoutUploadBatch`), not a session store or a signed hidden-form payload, holds the proposed candidates between upload and confirm.** This app has no session infrastructure, and a batch's `candidates` JSON can carry multiple base64 thumbnails per row — multi-KB apiece — which would be awkward to keep round-tripping through hidden form fields on every edit. The review screen instead loads the batch once, holds the ASPL's edits in ordinary React state in memory, and serializes the *current* edited state into one hidden field only at final submit. A batch nobody ever confirms is never explicitly expired; it's swept lazily, by age, the next time anyone starts a new upload (`uploadCampoutFile` deletes anything older than 24 hours before creating a new one) — there's no cron infrastructure in this app to schedule that proactively, and this app's usage pattern (an occasional bulk upload, not a high-frequency action) doesn't justify adding one.

## Alternatives Considered

- **Vercel Blob (or any object storage) for thumbnails**: the "obviously correct at scale" choice, rejected for now as unneeded complexity and a new secret/service at this app's actual data volume — see the Decision above and Requirement 30's Data Model Impact #3. Revisit if this app's image needs ever grow beyond a handful of small thumbnails a year.
- **Rendering PDF pages to a canvas (via `canvas` or `@napi-rs/canvas`) to get a thumbnail image**, rather than extracting embedded image XObjects directly: rejected before being tried, specifically to avoid `canvas`'s native-build risk on Windows (CLAUDE.md's standing caution about this Next version's unfamiliar territory). Reading pdf.js's own decoded image objects directly turned out to work and avoids the dependency entirely.
- **A two-pass extraction (segment first, then extract fields per segment)**: rejected as more Claude calls, more cost and latency, and more places for a document's campouts to get split incorrectly across passes, for no benefit this app's document sizes (capped at 30 pages/sheets) need.
- **Structured-output formatting for the Claude reply**: deferred for the same reason ADR 0021 deferred it — unverifiable without a live key in this build environment. Worth revisiting once one is available.
- **A keyword/heuristic fallback for a failed extraction call**: considered and rejected — see Decision above. There's no honest non-AI substitute for open-ended document segmentation; failing cleanly is more correct than guessing.
- **Chunking a large document across multiple Claude calls**: rejected for this version. The file-size (15MB) and page/sheet (30) caps exist partly to keep a single call's input comfortably within context limits, making chunking-and-stitching logic unnecessary complexity for documents this app actually expects to see.

## Consequences

- `ANTHROPIC_API_KEY`'s existing role (per ADR 0021) extends to a second, heavier call shape; no new secret is introduced by this requirement.
- `next.config.ts` now has a `serverExternalPackages` list and an `outputFileTracingIncludes` entry; any future package with its own relative-path-from-its-own-location assumption (worker scripts, native addons, bundled data files) should be checked against *both* failure modes — bundling relocation (dev) and trace-based deployment exclusion (production) are two different problems that happened to share the same root cause and symptom here, and fixing one didn't fix the other.
- Live extraction *accuracy* — the actual quality of segmentation and field extraction against real-world flyers — is unverified in this build environment, the same ceiling ADR 0021 documented for its own classification call. What's verified here is the full mechanical pipeline end-to-end (upload, parse, the clean failure path when the API call itself fails, the review screen's rendering of seeded candidates, and the transactional create/merge/delete-batch write on confirm) by running the app directly, not just unit tests.
- A campout's thumbnail, once uploaded, is baked into that row as a data URL — there's no shared image asset to deduplicate or garbage-collect across campouts, by design (see Requirement 30's Out of Scope).
