# Requirement 36 — Roster Import & Suggested Role Assignment

Status: Not started
Depends on: [Requirement 31 - Core Authentication: Accounts, Sessions & Passkeys](authentication-accounts/31-core-authentication-accounts-sessions-passkeys.md), [Requirement 33 - Adult/Guardian-Mediated Youth Account Creation (COPPA)](33-youth-account-creation-coppa.md), [Requirement 34 - Unit Membership, Invitations & Switching](34-unit-membership-invitations-switching.md) — accounts, youth-specific creation rules, and `Unit`/`UnitMembership` must already exist; this requirement is additive on top of them, not a replacement for any of their mechanics.

## Goal

Let a unit's ASPL (or adult leader) bulk-create accounts and unit memberships for their troop's existing roster by uploading a standard roster export, instead of inviting each of dozens of people one at a time through [Requirement 34](34-unit-membership-invitations-switching.md)'s normal invite flow — while never auto-assigning a role or permission. The import only *suggests* a role and patrol per person, based on the roster's own data; a human reviews and confirms every suggestion before anything is written, per this project's standing rule that AI-assisted bulk writes always pass through human review first.

## Source

User-provided example roster export (`RosterReport_Troop0332B_Troop_332_Roster_20261021.csv`, a BSA/Scoutbook-style troop roster), 2026-10-23, with the request to add roster-based account creation as its own dependency-ordered requirement in the authentication series and to analyze the file to determine what's actually needed.

## Source Data Shape — what the example roster actually contains

This matters enough to document explicitly, since the real file turned out to need more handling than "two sections, adults and youth":

- **Three structurally distinct sections, not two.** The file has `ADULT MEMBERS`, `YOUTH MEMBERS`, and a third `DEN CHIEF MEMBERS` block — each with its own column layout (the Den Chief section even uses a different header convention entirely: `User ID`, `Parent/Guardian Name 1`, `Address1`, trailing empty columns, clearly a different export template than the other two). Critically, the Den Chief rows are **not new people** — both Den Chiefs in the example (Derek Vangen, Theodore Hanks) already appear in the Youth section. A real roster file can repeat a person across sections; the importer must not create duplicate records for them.
- **The only reliable join key is the registration number** (BSA Number in this export), never name. Evidence in the example file itself: the same youth appears once per parent/guardian relationship (e.g. "Callum Leach" twice, "Joseph Skoglund" four times across two guardians each listed twice), which is legitimate duplication to collapse — but separately, two *adult* rows ("Aaron Neuman," BSA 136337477, and "Aaron Neumann," BSA 137479852 — same email, same address) are almost certainly one real person entered twice under two different numbers, which is a data-quality defect, not legitimate duplication. Name-based matching would handle these two cases backwards.
- **A youth row carries no youth email at all** — only a parent/guardian's name, relationship, address, phone, and email. This isn't a gap the importer needs to fill; it's the source data already matching [Requirement 33](33-youth-account-creation-coppa.md)'s "no personal youth email" design, for free.
- **`Positions (Tenure)` is the only field that maps to a ScoutBuddy role, and only reliably for youth.** `Patrol Leader [ Silver Fox] Patrol` ties directly to this app's Patrol Leader concept plus a specific patrol (corroborated by the row's own separate `Patrol` column). Nothing in the observed position vocabulary (Senior Patrol Leader, Assistant Senior Patrol Leader, Den Chief, Scribe, Quartermaster, Librarian, Troop Guide) says "ASPL of Camping" specifically — that's a troop-internal specialization on top of a BSA-registered title (most plausibly Assistant Senior Patrol Leader, but not reliably distinguishable from an ASPL with a different specialty). It can be suggested at best, never asserted.
- **Adult `Positions` data** (Scoutmaster, Troop Admin, Committee Chairman, Unit Treasurer, etc.) maps to no ScoutBuddy role at all in this pass — it's informational only, useful for identifying which adults are plausible candidates to mediate youth account creation ([Requirement 33](33-youth-account-creation-coppa.md)) or for a possible future unit-admin role ([Requirement 27](27-multi-tenant-unit-isolation.md)'s Out of Scope already flags that as deferred).
- **Every retained field splits cleanly into two kinds, matching this project's existing `User`/`UnitMembership` split**: person-level data that's the same no matter which unit's roster lists them (legal name, age bucket, gender, the member/registration number itself, address/phone, training certifications, BSA rank, school/grade, parent/guardian relationships), and unit-membership-level data that's genuinely about the relationship to *this* unit and can differ if the same person belongs to more than one (`Date Joined`, `Unit Number`, `Positions (Tenure)`, `Patrol`, `Swim Class`, `Swim Class Date`). REQ-36.10 below settles exactly which field goes where. (2026-10-23, confirmed with the user: Date Joined, Unit Number, Swim Class, Swim Class Date, Positions, and Patrol are unit-membership-level; everything else observed in the example file is person-level.)
- **A youth row's raw `Date of Birth` column is never persisted as-is.** [Requirement 33](33-youth-account-creation-coppa.md)'s REQ-33.8 converts it to a coarse age bucket (under 14 / 14-17 / 18+) at the moment it's read and discards the raw date — the adult section of the example file already arrives pre-bucketed this way (`"21 or more"`, `"18 to 20"`), so this isn't a new pattern for the data, just the same treatment extended to youth instead of left as an exact date.
- **The member/registration number is the join key, but not permanently fixed.** Scouting America is actively correcting longstanding duplicate/incorrect member numbers across its own systems — a person's number can legitimately change after this requirement's initial import has already run. This requirement's own matching (REQ-36.3) assumes the number is stable *at the time of one import*; handling a number that changes between imports, and reconciling any other roster drift over time, is [Requirement 37](37-roster-reconciliation-member-number-correction.md)'s job, not this one's.

## Requirements

- **REQ-36.1** The importer accepts a roster export file uploaded by an adult/ASPL, reusing this app's existing patterns rather than inventing new ones: direct-to-storage transport to avoid Vercel's request-body limit ([ADR 0032](../adr/0032-campout-upload-blob-transport.md)), and AI-assisted extraction followed by mandatory human review before any write ([Requirement 30](data-upload/30-campout-upload-from-pdf-excel.md) / [ADR 0031](../adr/0031-campout-upload-parsing-extraction-and-merge.md)). No AI-extracted roster data reaches the database until a human confirms it.
- **REQ-36.2** The importer handles a roster file containing multiple structurally distinct membership-type sections (at minimum adult and youth, as in the example; a third, overlapping section was also observed in real data). Each section's own column layout is parsed on its own terms. A person appearing in more than one section of the same file is recognized as one person, not created twice.
- **REQ-36.3** The stable identifier for deduplicating a person within and across sections, *for the duration of a single import*, is their registration number — never their name. Two rows with the same registration number are the same person; two rows with different registration numbers but suspiciously similar identity (same name, same email, same address) are flagged for human resolution, never silently merged or silently treated as unrelated. (This requirement does not handle a registration number that changes *between* separate import runs — that's [Requirement 37](37-roster-reconciliation-member-number-correction.md)'s REQ-37.1-37.4.)
- **REQ-36.4** A roster row repeated once per associated relationship (e.g. a youth row repeated once per parent/guardian) is collapsed into one person with multiple associated contacts, not imported as multiple accounts.
- **REQ-36.5** The import suggests, but never silently applies, a ScoutBuddy role and patrol per youth: a youth whose `Positions` field contains a recognizable Patrol-Leader-shaped title for a specific patrol is suggested as that patrol's Patrol Leader. No roster position maps reliably to "ASPL of Camping," so the importer never auto-assigns that role — it's always an explicit choice made by the reviewing human on the confirmation screen (REQ-36.6).
- **REQ-36.6** Every suggested role/patrol assignment is presented on a review screen — the same accept/edit/discard-before-confirm pattern [Requirement 30](data-upload/30-campout-upload-from-pdf-excel.md) already established for campout upload — before any `UnitMembership` row is created. This is not optional polish; it's this project's standing rule that an AI-extraction output never lands in the database in bulk without a confirm screen in front of it.
- **REQ-36.7** An imported youth account is created through [Requirement 33](33-youth-account-creation-coppa.md)'s adult-mediated path — the importing adult is that mediating adult, or is explicitly vouching that a named parent/guardian will complete the youth's own setup — using the roster's own guardian name/relationship/contact fields to pre-fill Requirement 33's guardian-contact field. The importer never invents or requires a youth email the source roster doesn't have.
- **REQ-36.8** An imported adult is never automatically granted any ScoutBuddy role. Their roster `Positions` data is retained and surfaced only as informational context for a reviewing ASPL — e.g. to help identify which adults are plausible mediators for youth accounts or candidates for a future unit-admin role — never as a permission grant.
- **REQ-36.9** A person who already matches an existing account in this unit (by registration number, or by an existing `UnitMembership`) is linked/updated, never re-created — mirroring [Requirement 30](data-upload/30-campout-upload-from-pdf-excel.md)'s existing merge-against-matched-record pattern for campouts. Re-running an import against the same roster file is safe and produces no duplicates.
- **REQ-36.10** Every field present in the roster is retained as informational data on the matched person — not just the minimum REQ-36.5-36.7 need for role suggestion and guardian contact. It's stored in the structure REQ-36.11 defines, clearly separated from this project's own operational data (never mistaken for, or used to silently derive, the confirmed `role`/`patrolId` a human actually set).
- **REQ-36.11** Retained roster data is split exactly along the person/unit-membership boundary: person-level fields (legal name, age bucket — never a raw date of birth, per REQ-33.8 — gender, the member/registration number, address, phone, roster-source email, training certifications and expirations, BSA rank, school/grade, and — for a youth — parent/guardian relationship records) live on the `User`, attached once regardless of how many units that person belongs to; unit-membership-level fields (`Date Joined`, `Unit Number`, `Positions (Tenure)`, `Patrol`, `Swim Class`, `Swim Class Date`) live on the `UnitMembership`, and can differ across two units the same person belongs to. This is a structural requirement, not a styling preference — mixing the two would mean a field that's actually per-unit (e.g. `Patrol`) gets silently treated as a single global fact about a person who belongs to two units, corrupting one or both.
- **REQ-36.12** For an adult, REQ-36.10's full retention applies with no further gate — an adult roster record goes well beyond [Requirement 33](33-youth-account-creation-coppa.md)'s minimization principle, which only ever applied to youth. For a youth, retaining anything beyond Requirement 33's own minimum (first name + last initial, unit-assigned username, guardian contact, age bucket) is gated behind that requirement's REQ-33.4 verifiable-parental-consent process — the same gate, not a new or looser one. A youth's full roster record (address, etc. — never a raw date of birth, which REQ-33.8 converts and discards regardless of consent status) can be retained once that consent is on file, never automatically just because it was present in the uploaded file.
- **REQ-36.13** Correcting a person's registration number after the fact, and reconciling any other roster data that changes between separate import runs, is [Requirement 37](37-roster-reconciliation-member-number-correction.md)'s job — this requirement's import only needs to get a person's data in correctly the first time.

## Acceptance Criteria

- [ ] Uploading the reference-shaped roster file produces one reviewable suggestion per unique person (by registration number), not one per row — including across the adult/youth/Den-Chief-style section boundary.
- [ ] No `User` or `UnitMembership` row is created until a human explicitly confirms the review screen.
- [ ] A youth with a "Patrol Leader [ <Patrol> ]"-shaped position is suggested as that patrol's Patrol Leader; no youth is ever suggested as "ASPL of Camping" automatically.
- [ ] A youth account created via import never has the youth's own email requested or stored; guardian contact is pre-filled from the roster's parent/guardian fields.
- [ ] Two adult rows that are plausibly the same real person at two different registration numbers are surfaced for human resolution, not silently merged or silently duplicated.
- [ ] Re-importing the same roster file does not create duplicate accounts or memberships for people already imported.
- [ ] Every roster field for a matched person is retained, stored on the correct side of the person/unit-membership split (REQ-36.11), and never used to silently derive or override a human-confirmed role or patrol assignment.
- [ ] A youth record's retained data beyond Requirement 33's minimum is never present without that requirement's verifiable-parental-consent gate having been satisfied first.
- [ ] A youth row's raw `Date of Birth` value never reaches storage in any form — only the under-14/14-17/18+ bucket it's converted to at read time.

## Out of Scope for This Requirement

- Automatic or unreviewed role/permission assignment of any kind — explicitly rejected by REQ-36.5/36.6/36.8 above.
- Any import source other than a file upload (e.g. a live Scoutbook API integration) — the file-upload shape matches this app's existing campout-upload precedent and needs no new transport mechanism.
- Creating the `Unit` itself — this requirement assumes the importing adult's `Unit` already exists per [Requirement 34](34-unit-membership-invitations-switching.md); roster import only populates membership within it.
- A dedicated unit-admin role for the adults this import surfaces as candidates — [Requirement 27](27-multi-tenant-unit-isolation.md)'s own Out of Scope already defers that.
- Correcting a registration number, or reconciling any roster data that changes between separate import runs — [Requirement 37](37-roster-reconciliation-member-number-correction.md).
