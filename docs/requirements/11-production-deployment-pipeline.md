# Requirement 11 — Production Deployment Pipeline & Environment Isolation

Status: Not started — documentation only
Depends on: [ADR 0003 - Postgres via Neon](../adr/0003-postgres-database-via-neon.md), [ADR 0004 - Vercel deployment via GitHub](../adr/0004-vercel-deployment-via-github.md), [ADR 0005 - Secrets kept in gitignored env files](../adr/0005-env-based-secrets-management.md), [ADR 0014 - Separate Neon branch for development and testing](../adr/0014-separate-dev-test-database-branch.md), and [Requirement 6 - Test Database Isolation](06-test-database-isolation.md) — this requirement closes the exact gap Requirement 6/ADR 0014 named as a known risk and left as a manual step.

## Goal

On 2026-10-14/15, the live Vercel deployment started throwing a generic server error on every page. The cause: Requirement 8's enum→table migration for patrols was applied to the `development` Neon branch (everything this project's tooling touches by default) and never applied to the `production` branch Vercel actually serves from — exactly the risk ADR 0014 named in its own Consequences section ("Skipping the second step means production silently falls behind the code that expects the new schema — worth catching before it ships") and that Requirement 6 left as an unchecked, manual acceptance criterion.

This requirement removes the human-memory step that failed. Going forward: which database a given piece of code talks to is a property of *where that code is running*, decided automatically and checked at startup — never something a person has to remember correctly — and shipping a schema change to production happens as an automatic, visible part of deploying to `main`, not a separate manual action someone might skip.

## Context: three independent pieces, each solving one part of the incident

**Environment-correct connections, enforced automatically.** `.env` keeps holding the `development` branch's `DATABASE_URL`/`DIRECT_URL`, exactly as today (ADR 0005) — used by `next dev`, `vitest`, and any ad hoc local Prisma command. A new `.env.production.local` holds the `production` branch's connection strings, for the one deliberate script below — the existing `.gitignore` pattern `.env*.local` already excludes it. This is the part that reverses ADR 0005/0014's original "production secrets never touch this project, only Vercel's dashboard" stance; seeing them only in Vercel's UI didn't prevent this incident, and having them available locally — gitignored, and only ever loaded by one script that announces itself loudly — is what makes the deliberate local migration path possible at all. A small, new **environment guard** (e.g. `lib/db-environment-guard.ts`, called once from `lib/db.ts` before the Prisma client is constructed) compares the resolved `DATABASE_URL`'s hostname against two known-safe hostname fragments, `NEON_DEVELOPMENT_HOST` and `NEON_PRODUCTION_HOST`. These are **not secrets** (a Neon host like `ep-fragrant-haze-b4zn25pb.c-6.us-east-2.aws.neon.tech` carries no credentials — the user/password are a separate part of the connection string) so they can live as plain committed constants, e.g. in `.env.example`'s comments or a tiny checked-in config file, unlike the connection strings themselves.

**Production migrations as part of shipping, not a separate step.** Vercel's Production build command (currently the Vercel default of `next build`) changes to `prisma migrate deploy && next build`. Vercel already injects Production-scoped `DATABASE_URL`/`DIRECT_URL` into every Production build's environment (that part of ADR 0014 was never the problem), so this runs `prisma migrate deploy` against the real `production` branch automatically, on every push to `main` (ADR 0004), before the new code that expects the new schema goes live — the direct fix for the actual incident. For the rare case a migration needs to be applied to production *before* the next deploy (recovering from today's situation, or an urgent hotfix), a new npm script, `migrate:production`, loads `.env.production.local` via Node's built-in `--env-file` flag (no new dependency — `dotenv-cli` was deliberately avoided per ADR 0005, and this doesn't need it either), prints the target host and how many migrations are pending, and requires typing a literal confirmation before running `prisma migrate deploy` — the command-line equivalent of this app's own confirm-before-destroying dialogs (`DeletePatrolDialog`, `RemoveFromCampoutDialog`). Both paths ultimately just run `prisma migrate deploy` — there is exactly one way production's schema ever changes, in two different contexts.

**Explicit, allow-list-only data flow between branches.** No application data crosses branches, in either direction, automatically or manually, by any tooling this requirement adds — `Campout`, `Menu`, `Meal`, `Dish`, `Ingredient`, `Review`, and `MealFrameworkException` rows stay wherever they were created. This isn't a new rule — it's ADR 0014's original isolation guarantee — but it's worth stating explicitly and permanently now that this requirement adds tooling that deliberately touches both branches from one place. The one thing that already ends up identical in both branches — the five seeded patrol rows from `20261014142438_patrols_table`'s hardcoded `INSERT` statements — isn't data copied *between* branches at all; it's the *same migration file* run independently against each branch, producing the same rows from the same source twice. This requirement names that as the only sanctioned form of cross-branch parity, categorically different from copying rows out of one database into another.

## Requirements

- **REQ-11.1** `.env.production.local` (gitignored via the existing `.env*.local` pattern) holds the `production` branch's `DATABASE_URL`/`DIRECT_URL`, alongside `.env`'s existing `development` values.
- **REQ-11.2** A startup guard compares the active `DATABASE_URL`'s hostname against known `development`/`production` Neon hostnames (committed as plain, non-secret constants) and throws before serving any request if `VERCEL_ENV === "production"` but the host isn't production's, or if running locally but the host *is* production's.
- **REQ-11.3** Vercel's Production build command runs `prisma migrate deploy` before `next build`, so every push to `main` applies any pending migration to the `production` branch automatically.
- **REQ-11.4** A new `migrate:production` npm script gives a deliberate, human-confirmed path to apply migrations to production outside of a deploy: it loads `.env.production.local` explicitly, prints the resolved host and pending-migration count, and refuses to proceed without an explicit typed confirmation.
- **REQ-11.5** Vercel Preview deployments are unaffected by REQ-11.2/11.3 — no preview-specific Neon branch or migration behavior is introduced by this requirement (see Out of Scope).
- **REQ-11.6** No tooling added by this requirement ever moves `Campout`/`Menu`/`Meal`/`Dish`/`Ingredient`/`Review`/`MealFrameworkException` rows between the `development` and `production` branches, in either direction.
- **REQ-11.7** The only sanctioned cross-branch parity is a migration's own seed `INSERT` statements running independently against each branch via REQ-11.3/11.4 — never a copy step between two already-existing databases.

## Decisions assumed (flag if these aren't what you want)

- **A static `.env.production.local` file, kept up to date by hand**, rather than pulling it on demand with `vercel env pull --environment=production`. The static file works without being logged into the Vercel CLI locally and makes exactly what's stored visible; the tradeoff is that if the Neon production credentials are ever rotated, this file needs a manual update too. Say so if you'd rather the script pull fresh credentials from Vercel each time instead.
- **The environment guard hard-fails** a Production build/boot on a host mismatch, rather than warning and continuing. A silent continue is exactly the class of failure this requirement exists to close, so I'm assuming "fail loudly and refuse to serve" is the right default — not "log a warning and hope someone notices," which is close to what happened this time.
- **Typed-confirmation, not a `--yes` flag**, guards `migrate:production` — consistent with the app's own UI pattern of requiring an explicit, hard-to-misclick action before anything destructive, rather than a flag that's easy to habitually include in a copy-pasted command.

## Acceptance Criteria

- [ ] `.env.production.local` exists locally with real production connection strings and is confirmed excluded from git by the existing `.env*.local` pattern (no new `.gitignore` rule needed).
- [ ] `next dev`, `npx vitest run`, and a bare `npx prisma ...` command read only `.env` — never `.env.production.local` — verified by inspecting which values each resolves to.
- [ ] `npm run migrate:production` prints the resolved host and pending-migration count, and refuses to run `prisma migrate deploy` without the exact typed confirmation.
- [ ] Vercel's Production build command runs `prisma migrate deploy` before `next build`; a push to `main` carrying a pending migration applies it automatically with no manual Vercel/Neon step — the scenario that failed on 2026-10-14 reproduced and shown fixed.
- [ ] A Production build/boot whose `DATABASE_URL` host doesn't match the known production host fails immediately and loudly, before serving any request.
- [ ] A local `next dev` boot whose `.env` host matches the known production host fails immediately and loudly.
- [ ] No command this requirement adds ever writes to, reads for copying, or otherwise moves `Campout`/`Menu`/`Meal`/`Dish`/`Ingredient`/`Review`/`MealFrameworkException` rows between the `development` and `production` branches.
- [ ] The only observed cross-branch parity is identical seed rows produced by the same committed migration file running independently against each branch — not by any copy step.

## Out of Scope for This Requirement

- Vercel Preview deployments' environment and migration behavior — no preview workflow or preview-specific Neon branch exists yet in this project; this is worth a follow-up requirement once preview deploys are actually in use (Requirement 6 already flagged Neon's per-preview ephemeral branches as a future option, not required now).
- Rotating the current Neon credentials — ADR 0005 already flagged this as a separate, low-cost precaution; unrelated to this requirement's scope.
- Any mechanism for seeding genuinely new shared reference data outside of a migration's own `INSERT` — not needed today (see the data-flow section above), and deliberately not built preemptively.
- A secrets manager or Vercel-CLI-based on-demand credential pulling — a static gitignored file was chosen instead (see Decisions Assumed); revisit only if credential rotation makes the static file painful to maintain.
- Any change to how the application itself behaves at runtime — this requirement is entirely about deployment/tooling, not app features.
