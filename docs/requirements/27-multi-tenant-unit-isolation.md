# Requirement 27 — Multi-Tenant Unit Isolation & Switching

Status: Not started
Priority: High — per explicit user direction (2026-10-18), this is the first thing to build once its auth prerequisite exists; do not let it drift to the back of the backlog behind unrelated polish requirements.
Depends on: a not-yet-written user authentication requirement (replacing [ADR 0010](../adr/0010-cookie-based-role-identity.md)'s cookie-based role identity with real accounts) — this requirement assumes that prerequisite is complete and does not itself specify login mechanics (password reset, SSO, session tokens, etc.). No code changes for Requirement 27 itself happen before that prerequisite lands; this document is kept current and ready to build from, not implemented ahead of it.

## Goal

Make every piece of troop data in ScoutBuddy strictly isolated per chartered **Unit**, so the same deployment can serve 100+ unrelated units with zero possibility of one unit seeing, editing, or inferring another's data — while letting a person who genuinely belongs to more than one unit (e.g. an adult who volunteers with two units) switch between them without re-authenticating — and do so on infrastructure that stays cost-effective at that scale.

## Terminology

The ask uses "organization"; this requirement uses **Unit** instead — the actual BSA term for a chartered Troop/Pack/Crew/Ship/Post, i.e. the tenant boundary itself, per CLAUDE.md's domain-language rule. `Organization`/`org` may still appear informally in multi-tenancy literature, but user-facing copy, code identifiers (`unitId`, `UnitMembership`), and this document all say **Unit**. A Unit is the thing a Patrol, Campout, Menu, etc. belongs to — distinct from a Patrol, which remains a subdivision *within* one unit (ADR 0018). Using "Unit" rather than a generic "Organization" also keeps the door open for ScoutBuddy to eventually serve Packs or Crews, not only Troops, without a second rename.

## Source

User request, 2026-10-18: ensure the entire system is multi-tenant capable; document everything required for multiple unique units to use the system; assume a future auth system where some users belong to multiple units and need to switch between them easily; no data should ever leak between units; privacy practices should follow industry standards. Follow-up, same day: use "Unit" instead of "Troop" as the tenant term, and validate that the architecture this is built on is cost-effective and supports 100+ units.

## Why This Matters Now

ScoutBuddy was built single-tenant on purpose ([ADR 0010](../adr/0010-cookie-based-role-identity.md): "revisit if ScoutBuddy is ever used somewhere... shared across multiple troops"). Every table today (`Campout`, `Patrol`, `Menu`, `Comment`, etc.) is global — there is no column anywhere that says which unit a row belongs to. Retrofitting tenancy after the fact, rather than designing it in from the start of a second unit's onboarding, is exactly the kind of change that's cheap to get right early and expensive to get right once multiple units' real data already coexist ungated in the same tables. This requirement exists to specify the shape of that change *before* a second unit is onboarded, not after.

## Architecture Validation — Cost & Scale at 100+ Units

CLAUDE.md requires reading the existing ADRs before proposing a stack or data-model change. The current stack ([ADR 0001](../adr/0001-hosted-web-app-architecture.md) hosted web app, [ADR 0003](../adr/0003-postgres-database-via-neon.md) Postgres via Neon, [ADR 0004](../adr/0004-vercel-deployment-via-github.md) Vercel) was chosen for a single five-person troop on free tiers. This section validates whether it still holds at 100+ units before this requirement commits to it.

**Data volume is small regardless of unit count.** ScoutBuddy's per-unit data is a handful of campouts per term, each with a handful of patrol menus, each with a handful of meals/dishes/ingredients — a few thousand rows per unit per year at most, not a data-intensive workload. 100 units is a fan-out of *tenants*, not of data volume per tenant; total storage at 100+ units is still plausibly in the low gigabytes, not terabytes.

**Shared-schema (one database, every table carries `unitId`) is the cost-effective and operationally simplest model at this scale — not database-per-unit or schema-per-unit.** A separate Neon project/branch per unit would multiply per-project overhead and, per Neon's own plan limits, push against branch-count ceilings designed for dev/preview branching, not per-customer multiplication — the wrong tool for 100+ tenants. A single shared database with an indexed `unitId` column (and RLS enforcing it, REQ-27.5) is the standard, proven pattern for this tenant count and data shape, and is what this requirement's REQ-27.1/27.5 already describe — this validation confirms that direction rather than changing it.

**Row-Level Security overhead is negligible when the tenant column is indexed.** Practitioner reports on comparable shared-schema RLS setups show per-query overhead on the order of a fraction of a millisecond once the policy column (`unitId`) has a standard B-tree index; the real risk is an *unindexed* tenant column turning every query into a full table scan. This requirement's REQ-27.5 is updated below to make indexing the `unitId` column mandatory, not optional, precisely to avoid that failure mode.

**Estimated infrastructure cost stays modest at 100+ units**, based on Neon's and Vercel's published usage-based pricing as of late 2026 (confirm exact current figures at neon.com/pricing and vercel.com/pricing before budgeting, since both are usage-based and change over time):

- *Neon*: ScoutBuddy's traffic pattern (youth leaders checking in sporadically, not sustained concurrent load) suits Neon's autosuspend/scale-to-zero compute billing — paying only for actual active compute time, not for 100 units' worth of always-on servers. Storage for low-gigabyte total data is a small, flat monthly cost. This is comfortably within a single paid Neon plan one tier above free, not a jump to an enterprise-scale commitment.
- *Vercel*: a single Next.js deployment serves all 100+ units from the same app — hosting cost doesn't scale per-tenant, only with aggregate request/bandwidth volume, which stays modest for this app's usage pattern even at 100+ units.
- **This project stays non-commercial** — no revenue model, no per-unit billing (also reflected in Out of Scope below) — so there is no ToS-driven requirement to move off Vercel's free Hobby tier purely because multiple independent units are served; Hobby's own restriction is on *commercial* use, not multi-tenant use as such. What still needs a plain capacity check, independent of ToS, is whether Hobby's usage caps (bandwidth, function-execution minutes) hold up against 100+ units' *aggregate* traffic — flagged as REQ-27.20 below as a check, not an assumed upgrade.

**Conclusion: the existing stack (Next.js + Postgres-via-Neon + Vercel) is validated as cost-effective and sufficient for 100+ units**, provided (a) tenancy is implemented as shared-schema with an indexed `unitId` + RLS rather than per-unit databases/schemas, and (b) whichever provider tiers are in use (free or paid) are re-checked against then-current usage caps as real unit count grows — staying non-commercial does not by itself guarantee headroom under a free tier's *capacity* limits, only that there's no ToS pressure to upgrade for revenue reasons. No stack change is needed to hit this scale target. The exact provider plan tier and migration mechanics remain a build-time ADR per CLAUDE.md's working conventions (see REQ-27.5's note) — this section validates the *direction*, not the final dollar figures, which should be re-confirmed against current pricing/limits as real unit count grows.

## Principles (non-negotiable for this requirement)

- **Isolation is the default, not an exception.** Every query that reads or writes unit-scoped data must be scoped to a unit; there is no "forgot to filter" failure mode that silently returns another unit's rows instead of erroring or returning nothing.
- **Defense in depth.** Isolation must not depend on every developer remembering to add a `WHERE unitId = ...` clause to every query, forever. At least one enforcement layer must sit below the application code itself (see REQ-27.5).
- **Membership, not re-authentication, drives switching.** A person who belongs to multiple units signs in once; moving between units they belong to is a UI action, not a new login.
- **Minors' data gets extra care.** Per FEATURES.md, Patrol Leaders and the ASPL of Camping are youth. Any requirement-27 design must account for data-privacy obligations around minors (see REQ-27.9), not just adult-equivalent handling.
- **Scale cheaply, not just correctly.** A technically-isolated design that only stays affordable at 5 units isn't good enough — every isolation mechanism chosen must also hold up, cost-wise, at the 100+-unit target validated above.

## Requirements

### Data model & isolation

- **REQ-27.1** A new `Unit` entity is the root of the tenancy boundary. Every existing entity that is unit-specific data — `Patrol`, `Campout`, `Menu`, `Meal`, `Dish`, `Ingredient`, `Review`, `Comment`, `CommentActivity`, `MealFrameworkException`, and any entity added by a future requirement — carries a `unitId` foreign key, whether directly or (where the existing schema already guarantees a single-hop relation to an already-scoped parent) enforced via that parent at the database level. The exact column layout (direct `unitId` on every table vs. relying on parent joins for some) is a real schema decision and gets its own ADR at build time, per CLAUDE.md's working conventions — this requirement specifies the invariant, not the column-by-column migration.
- **REQ-27.2** Global, non-unit-specific reference data stays global and does not get a `unitId`: the six standard meal-framework occasions (`MealOccasion`) describe a BSA-wide convention, not unit-specific data, and are shared as today. `Patrol` rows, by contrast, are already unit-specific per ADR 0018 (admin-managed, one unit's own roster of patrols) and must gain a `unitId`.
- **REQ-27.3** No foreign key may ever cross a `unitId` boundary — e.g. a `Menu` in Unit A can never reference a `Patrol` or `Campout` belonging to Unit B. This is enforced both by application-level checks at write time and by the database-level defense-in-depth layer (REQ-27.5).
- **REQ-27.4** Every unique constraint that's implicitly per-unit today (e.g. `Menu`'s `@@unique([campoutId, patrolId])`) continues to hold per-unit once `unitId` exists, since `campoutId`/`patrolId` are themselves already unit-scoped — no change needed to those specific constraints, but any *new* constraint added by a future requirement must be checked against this same per-unit assumption rather than assumed global.
- **REQ-27.5** The tenancy model is **shared-schema**: one Postgres database, every unit-scoped table carries `unitId`, not a database- or schema-per-unit split (confirmed cost-effective and standard-practice for this data volume and tenant count by the Architecture Validation section above — Neon per-project/branch overhead and limits make per-unit databases the wrong fit for 100+ units). Every `unitId` column is covered by a standard index, without exception — an unindexed tenant column is the one condition under which Row-Level-Security-style isolation gets expensive, per the validation above, so this is mandatory, not a tuning nice-to-have. On top of application-level filtering, at least one enforcement mechanism sits below the application code (Postgres Row-Level Security keyed off a per-request session variable, e.g. `current_setting('app.current_unit_id')`, or an equivalent compile-time-enforced query layer) so that a query that forgets an explicit unit filter cannot return or mutate another unit's rows. The exact RLS policy syntax vs. an alternative compile-time-enforced layer is a build-time ADR; the shared-schema-plus-indexed-column-plus-sub-application-enforcement *shape* is settled by this requirement.
- **REQ-27.6** A cross-tenant isolation test suite exists and runs as part of `npm test` (same spirit as [ADR 0014](../adr/0014-separate-dev-test-database-branch.md)'s test-database isolation): seed two (or more) units' worth of data, then assert that every read/write path, when invoked as a member of Unit A against a Unit B resource ID, returns a not-found/forbidden result and never Unit B's data — not just for happy-path pages, but for every Server Action that takes an ID. Seed at least one test fixture with a unit count in the dozens, not just two, to catch index/query-plan regressions that only show up once a table holds many units' worth of rows.

### Accounts, membership & switching

- **REQ-27.7** A `UnitMembership` join table associates a `User` with a `Unit` and a role (`PATROL_LEADER` or `ASPL`, extending today's `Actor` concept from ADR 0010/0026) plus, for a Patrol Leader, which `Patrol` they lead. A single user can hold memberships in more than one unit simultaneously, and a user's role is scoped per-membership — the same person can be the ASPL in one unit and a Patrol Leader in another.
- **REQ-27.8** The signed-in person's active unit is tracked server-side (e.g. `activeUnitId` on their session), not inferred from a request parameter alone, and is revalidated against the user's actual memberships on every request — a tampered or stale `activeUnitId` must never grant access to a unit the user isn't a member of. This extends ADR 0010's principle ("the cookie is trusted as identity, but never as authorization on its own") to unit scope: membership is checked server-side on every Server Action, the same way role-based permission is checked today in `lib/permissions.ts`.
- **REQ-27.9** A unit switcher is reachable from anywhere in the app (e.g. in the header, alongside or replacing today's role picker) and lists only the units the signed-in person actually belongs to. Switching is a single action that updates the active-unit session value and returns the person to an equivalent page scoped to the new unit (e.g. the dashboard), never leaving them on a page still showing the previous unit's data mid-navigation.
- **REQ-27.10** Joining a second unit happens through an explicit, auditable action (an invite from that unit's ASPL, or an invite code) — never automatic or inferable from matching email domains, names, or any other heuristic. A user is never silently added to a unit they didn't take an action to join.

### Authorization enforcement

- **REQ-27.11** Every existing permission check in `lib/permissions.ts` (`canEditMenu`, `canSubmitMenu`, `canReview`, etc.) is extended to also verify the resource being acted on belongs to the actor's active unit — a correct role (e.g. "I am an ASPL") is necessary but no longer sufficient; the ASPL must be *this unit's* ASPL for *this* resource's unit.
- **REQ-27.12** Unit-scoping is enforced identically whether a request comes through a page load, a Server Action, or any future API route — there is no back-door path (an API route added later, a cron job, an export endpoint) that reads unit data without going through the same unit-scoping layer as everything else.

### Privacy & compliance

- **REQ-27.13** Data isolation extends to anything derived from unit data, not just primary rows: aggregate counts, search/autocomplete suggestions, error messages, and logs must never reveal another unit's data (e.g. an error message must not leak "a campout with that name already exists" if the colliding campout belongs to a different unit).
- **REQ-27.14** Personal data collected about a person (name, email, and anything else the eventual auth requirement adds) is handled per data-minimization principles: only what's needed to run the app is collected, and it's retained only as long as the person's unit membership is active plus a documented retention window after removal/deletion, not indefinitely by default.
- **REQ-27.15** A unit admin (the ASPL role, or a future dedicated unit-admin role) can request export of their unit's data and deletion of their unit's data in its entirety — a unit that stops using ScoutBuddy can get its data out and/or have it removed, consistent with standard data-portability and right-to-erasure practices (GDPR Art. 15/17, CCPA-equivalent), even though ScoutBuddy's primary user base may be US-based.
- **REQ-27.16** Because Patrol Leaders and the ASPL of Camping are youth (FEATURES.md), any personal data collected about them under the future auth system is evaluated against COPPA (for any user plausibly under 13) and general minor-data-handling best practice before launch — e.g. preferring a parent/guardian or unit-adult-leader-mediated account-creation flow over a youth member self-registering with their own email, if that's what the eventual auth design does. This requirement doesn't resolve that design (it belongs to the auth prerequisite) but flags it as a hard gate that must be explicitly addressed, not defaulted into, before any unit with real youth accounts goes live.
- **REQ-27.17** Transport is already encrypted (Vercel/TLS) and at-rest encryption is already Neon's default — this requirement doesn't change either, but any new credential, invite-token, or session-secret introduced to support multi-unit membership follows [ADR 0005](../adr/0005-env-based-secrets-management.md)'s existing secrets-management approach rather than inventing a new one.
- **REQ-27.18** Access to cross-unit operational data (e.g. a future internal admin view for the ScoutBuddy operator, if one is ever built) is itself logged — who looked at which unit's data and when — so that even legitimate operator-level access is auditable, not just unit-to-unit access.

### Migration & operations

- **REQ-27.19** Today's single unit's worth of existing data is backfilled into exactly one real `Unit` row as part of the migration that introduces `unitId` — existing campouts, patrols, menus, etc. are not deleted or orphaned, matching the hand-written-migration-with-backfill style ADR 0018 already established for a similar structural change.
- **REQ-27.20** Before a second real unit is onboarded, and periodically as unit count grows toward 100+, confirm the project's current Vercel and Neon plan tiers still have enough *capacity* headroom (bandwidth, function-execution minutes, compute, storage) for the actual aggregate traffic/data at that point — this stays a non-commercial project, so the check is purely about usage caps, not a ToS-driven requirement to move to a paid tier. This is an operational check, not a code change, but it belongs in this requirement because "no stack change needed" (the validation's conclusion) is conditional on actually having headroom under whichever tier is in use.

## Acceptance Criteria

- [ ] Every unit-specific table has a `unitId` (directly or via an enforced single-hop parent relation), every `unitId` column is indexed, and the six standard meal-framework occasions remain the one piece of shared, non-unit-scoped reference data.
- [ ] A cross-tenant isolation test suite runs in `npm test`, seeded with dozens of units' worth of data, and fails if any read/write path returns or mutates another unit's data when invoked with a mismatched unit context.
- [ ] At least one isolation enforcement layer exists below application code (e.g. Postgres RLS) in addition to application-level filtering.
- [ ] A person with memberships in two units can switch their active unit from a reachable control and immediately see only the new unit's data everywhere in the app — no page continues to show the previous unit's data after switching.
- [ ] A person is never added to a unit without an explicit, auditable join action (invite or invite code) — no automatic membership inference.
- [ ] Every existing permission check additionally verifies the acted-on resource belongs to the actor's active unit, and this is verified with a test that a correct role in the wrong unit is still rejected.
- [ ] A unit admin can request export and full deletion of their unit's data.
- [ ] The eventual auth design's handling of youth-collected personal data has an explicit, documented answer to the COPPA/minor-data question (REQ-27.16) before any unit with real youth accounts goes live — "not yet decided" is not an acceptable launch state.
- [ ] Existing single-unit data is backfilled into one real `Unit` row with no data loss as part of the migration.
- [ ] Before onboarding a second real unit, the project's Vercel and Neon plan tiers are confirmed to have enough capacity headroom (bandwidth, function-execution minutes, compute, storage) for the projected traffic/data — purely a usage-cap check, since the project stays non-commercial and is not required to move off a free tier for ToS reasons.

## Out of Scope for This Requirement

- The authentication mechanism itself (login method, password/SSO, session token format, account recovery) — belongs to this requirement's auth prerequisite, not here.
- Billing, subscription tiers, or any per-unit pricing model charged to the units themselves.
- Per-unit custom domains, white-labeling, or branding beyond what ADR 0017's existing theme already supports.
- Data residency / regional hosting requirements (e.g. EU-only hosting) — not currently a stated need; revisit if a unit with such a requirement is ever onboarded.
- Designing the exact `unitId` migration SQL or choosing the specific RLS policy syntax vs. an alternative enforcement mechanism — both are real implementation decisions deferred to their own ADR(s) at build time, per CLAUDE.md's working conventions, same pattern this project already follows (see REQ-25.1's "must get its own ADR if so"). The Architecture Validation section above settles the *shape* (shared schema, indexed column, sub-application enforcement) but not the final syntax.
- Re-architecting to database-per-unit or schema-per-unit — explicitly considered and rejected by the Architecture Validation section above as the wrong fit for 100+ units on Neon.
- A dedicated unit-admin role distinct from the ASPL, if one turns out to be needed beyond what REQ-27.15 requires — the ASPL role is assumed sufficient for unit-admin actions in this pass unless a future requirement says otherwise.
