# Requirement 12 — Menu Print Preview & Shopping List

Status: Not started — documentation only
Depends on: none directly, but reuses [Requirement 1 - Core Approval Loop](01-core-approval-loop.md)'s `Menu`/`Meal`/`Dish`/`Ingredient` data model as-is, and [Requirement 4 - Meal-Framework Variation](04-meal-framework-variation.md)'s occasion ordering (`MEAL_OCCASIONS`)

## Goal

A Patrol Leader needs a physical, take-to-the-campsite reference: what to cook, what it needs, and a way to check items off while shopping. Today's menu page (`/menus/[id]`) is an editing/review screen — forms, remove buttons, status chips — not something anyone would want to print and tape to a cooler lid. This requirement adds a dedicated, print-optimized view of one patrol's menu for one campout: a cooking reference (page 1) and a shopping list with handwrite-to-check boxes (page 2), viewable on-screen exactly as it will print before anyone actually prints it.

## Context: what already exists vs. what's new

Every field this needs already exists — `Campout.name`/`date`, `Patrol.name`, `Menu.allergyNote`/`nutritionNote`, and the full `Meal` → `Dish` → `Ingredient` tree, all already loaded together by the existing `/menus/[id]` page's own query. Nothing about the data model needs to change. What's new is entirely presentational: a second, print-tuned view of the same `Menu`, plus the CSS/layout work to make it paginate predictably at 8.5"×11".

## Requirements

- **REQ-12.1** A "Print preview" entry point appears on `/menus/[id]`, linking to a new, dedicated print view of that same menu.
- **REQ-12.2** The print view shows, on what will print as **page 1**: the campout name and date, the patrol's name (and color, consistent with how the patrol is identified everywhere else in the app), the menu's allergy note displayed prominently (not buried at the bottom the way today's edit page does), and every meal occasion that has dishes, in the same fixed order used everywhere else (`MEAL_OCCASIONS`), each listing its dishes by name with that dish's full ingredient list (name and quantity) beneath it, in a visibly smaller font than the dish name — this is what the Patrol Leader actually reads while standing at the stove, not just a table of contents for page 2.
- **REQ-12.3** The print view shows, on what will print as **page 2**: a shopping list covering every ingredient, across every dish, across every meal on this menu — each row showing the ingredient's name and quantity exactly as entered, with a printed checkbox-style box next to each row for handwriting a checkmark once purchased (not an interactive form control — this is read by a human holding a pen, not a browser). Rows are grouped into grocery-store-style categories (Produce, Meat & Protein, Dairy & Eggs, etc. — see REQ-12.9) rather than by dish or meal; each row instead carries a small per-item indicator naming which meal occasion it's for. Two dishes both needing "Chicken breast" produce two separate rows, never merged into one combined quantity — this is a shopping list for buying ingredients once per dish's need, not a pantry-inventory total.
- **REQ-12.4** The page is laid out for a standard 8.5"×11" sheet with 1-inch margins on all sides (`@page { size: letter; margin: 1in; }`), and the page break between page 1 and page 2 is explicit (the menu content and the shopping list never share a printed page).
- **REQ-12.5** The on-screen preview renders the same content with the same pagination the browser's print will actually produce — margins, page break, and overall proportions visible before anyone opens the print dialog — rather than a different-looking screen layout that only becomes "the real thing" once printed.
- **REQ-12.6** The print view carries no app chrome (header, navigation, role switcher) — on screen or on paper — so what's visible is only ever the menu content itself.
- **REQ-12.7** The print entry point and view are available to the Patrol Leader viewing their own patrol's menu and to the ASPL of Camping viewing any patrol's menu — the same two audiences who can already reach `/menus/[id]` today.
- **REQ-12.8** As content volume grows, page 1's dish list and page 2's shopping list shrink (smaller text, tighter spacing) to keep fitting within 2 pages — but never below **8pt** text. A menu whose content still doesn't fit at 8pt overflows onto a third (or further) page rather than shrinking past that floor. Confirmed: legibility has a hard lower bound; the page count doesn't. (Page 1 now carries full ingredient lists per REQ-12.2, not just dish names — this makes the shrink behavior load-bearing more often than originally expected, not just an edge case for unusually large menus.)
- **REQ-12.9** Each ingredient's grocery category is inferred automatically from its name — the Patrol Leader never tags or picks a category when adding an ingredient (`addIngredient` takes only `name`/`quantity` today, unchanged). An ingredient that can't be confidently categorized goes into a catch-all **"Other"** category, placed last, rather than being guessed into the wrong aisle. Within a category, rows are ordered so identical/similar ingredient names fall next to each other (e.g. both dishes' "Chicken breast" rows are adjacent) without being merged (REQ-12.3).

## Decisions assumed (flag if these aren't what you want)

- **Category inference is a maintained keyword/lookup heuristic, not a live AI call.** A new, pure, unit-tested helper (e.g. `lib/ingredient-categories.ts`, in the same style as `lib/dates.ts`/`lib/progress.ts`) matches each ingredient's `name` against curated keyword lists per category — no network call, no added infrastructure, deterministic and testable, consistent with this being a Vercel-hosted app with no background services (ADR 0001/0002). It will be imperfect for unusual or compound ingredient names ("corn tortillas" could plausibly read as Produce or Bakery) — "Other" exists specifically to absorb that gracefully rather than have the app confidently guess wrong. This trades some accuracy for zero added cost/latency/dependency versus an LLM-based categorization call; flag if the accuracy tradeoff isn't acceptable.
- **Proposed category list and order** (a typical grocery store's rough walk order, not alphabetical): Produce → Meat & Protein → Dairy & Eggs → Bread & Bakery → Pantry & Dry Goods → Condiments & Sauces → Spices & Seasonings → Frozen → Beverages → Other (always last). Real store layouts vary; this is a reasonable default, not something the app can know is correct for any specific store. Say so if you want a different category list or order.
- **Within a category, rows are sorted alphabetically by ingredient name.** This is what naturally puts "similar ingredients next to each other" (per your request) without needing fuzzy-matching logic to decide what counts as "similar" — two dishes' "Chicken breast" rows land adjacent because they're spelled the same, not because anything detected they're related.
- **The per-item meal indicator shows the occasion (e.g. "Sat. Dinner") and, space permitting, the dish name** — both are already known per `Ingredient` → `Dish` → `Meal`, and keeping the dish visible alongside the occasion preserves the context the original dish/meal-grouped design had, just as a label instead of a grouping. Say so if you want occasion only, no dish name.
- **No new view-permission gate.** `/menus/[id]` has no access restriction today — anyone who reaches the URL can view it, role gating only controls which *actions* (edit, submit, approve) are available. The print view follows the same existing pattern rather than introducing the app's first "who can view this" check. If you want printing specifically restricted to just the owning Patrol Leader and the ASPL (tighter than viewing the menu itself already is), that's new access-control logic, not something already established elsewhere to extend.
- **The menu's status and approval history don't appear on the print view.** They're relevant to the approval workflow, not to someone standing at a camp stove; omitted to keep page 1 focused. The nutrition/MyPlate note *is* included alongside the allergy note (same kind of existing data, shown together) unless you'd rather leave it off.

## Acceptance Criteria

- [ ] `/menus/[id]` has a working "Print preview" link/button, visible to anyone who can already view that menu.
- [ ] The print view's on-screen rendering visibly shows two distinct 8.5"×11"-proportioned pages with 1-inch margins and a clear break between them — not a single continuous scroll that only becomes paginated once actually printed.
- [ ] Page 1 shows the campout name and date, the patrol's name, the allergy note (prominently), and every occasion with dishes in the correct fixed order, each listing its dishes with that dish's ingredients beneath it in a visibly smaller font than the dish name.
- [ ] Page 2 shows every ingredient from every dish on the menu, each with its quantity and a printable checkbox, grouped into grocery-style categories in a sensible aisle order (ending in "Other"), with same-named ingredients from different dishes appearing as separate, adjacent rows rather than one merged row, and each row tagged with which meal it's for.
- [ ] Adding an ingredient to a dish requires no new data entry (no category picker) — categorization is fully automatic from the ingredient's existing name.
- [ ] Using the browser's actual print function (or print-to-PDF) on this view produces output matching the on-screen preview: two pages, 1-inch margins, no app header/nav visible anywhere.
- [ ] A menu with zero dishes, and a menu with an unusually large number of dishes/ingredients, both render sensibly (empty state handled gracefully; a large menu shrinks toward fitting 2 pages rather than silently truncating data).
- [ ] Shrinking stops at 8pt text — a menu large enough to still overflow at 8pt spills onto a third page at 8pt rather than continuing to shrink past it.

## Out of Scope for This Requirement

- Any change to `/menus/[id]` itself beyond adding the print entry point — this is a new, separate view, not a redesign of the existing editing/review page.
- Printing anything other than one patrol's one menu at a time (e.g., a combined print of every patrol's menu for a campout) — one Patrol Leader, one campout, one print view, matching how the rest of the app scopes a `Menu`.
- PDF generation via a server-side library (e.g. a headless-browser or PDF-rendering service) — this uses the browser's own native print/print-to-PDF, consistent with this being a Vercel-hosted app with no background job infrastructure (ADR 0001/0002).
